# v0.1.3 Type Discovery and Reflection Safety Specification

## 1. Purpose and status

This specification turns the discovery and exception-isolation requirements in the v0.1.3 Metadata Probe Implementation Plan into an implementable, reviewable contract. It is design-only. It does not authorize C# implementation, compilation, packaging, installation, or game execution.

The probe is a read-only metadata inventory. It is not a runtime object inspector, registration experiment, or proof of game behavior. The target type/member surface recorded in the Landmark API Evidence Matrix is transcribed from prior audit notes, not a fresh inspection of the target game's raw assemblies. Exact target-build metadata and IL remain required before semantic conclusions or implementation.

## G0.3.1 output reservation proposal

The proposed output-budget reservation algorithm is documented in [G0.3.1 Output Budget Reservation Protocol](v0.1.3%20G0.3.1%20Output%20Budget%20Reservation%20Protocol.md). It remains non-normative pending explicit G0 adoption.

## 2. Required target set and matching policy

The required target short-name allowlist contains exactly these nine names:

1. `Landmark`
2. `LandmarkData`
3. `AsyncedLandmark`
4. `SceneLoader`
5. `AssetBundleManager`
6. `AssetBundleHooker`
7. `ChunkManager`
8. `ChunkPoint`
9. `ChunkPointType`

### 2.1 Candidate discovery is not type resolution

- Compare `Type.Name` to the allowlist using ordinal, case-sensitive equality. This is a discovery filter only.
- Do not treat a short-name match as a unique identity.
- Record each candidate's `FullName` (or `UNKNOWN`), assembly full identity, module name, declaring type, base type and visibility.
- If the repository later acquires exact namespace-qualified identities from target-build evidence, add them as explicit expected `FullName` values in a separately reviewed allowlist revision. Do not infer namespaces from short names.
- If an expected `FullName` is configured, only exact ordinal `FullName` matches qualify. Still report all same-short-name candidates as context.
- If no expected `FullName` is configured, a target is RESOLVED only when exactly one candidate exists across the inspected loaded assemblies. Zero candidates is NOT_FOUND; two or more candidates is AMBIGUOUS.
- A duplicate `FullName` in different assemblies is also ambiguous. Assembly identity is part of type identity; never collapse candidates merely because their `FullName` strings match.
- Never choose the first result, the first loaded assembly, the first namespace match, or a candidate based on enumeration order.

### 2.2 Candidate cap

The maximum retained/emitted candidate identities is 8 per target short name. Examine and count every exact short-name match in each successfully inspected assembly, but retain only a bounded top-8 set keyed by the deterministic identity tuple in §4; do not accumulate an unbounded list for later sorting. Emit retained identities in deterministic order. If assembly inspection or type enumeration is incomplete, report observed-so-far count and total UNKNOWN. If more than 8 candidates are observed, emit TRUNCATED, mark PARTIAL and do not resolve the target, even if only one retained candidate appears plausible. If stable identity formatting fails, use a bounded fallback descriptor, mark ordering uncertain/PARTIAL and never use discovery order as a tie-breaker.

## 3. Assembly enumeration

1. Call the loaded-assembly enumeration once per run. Do not call `Assembly.Load`, `LoadFrom`, `LoadFile`, `ReflectionOnlyLoad`, or any other assembly-loading API.
2. Sort the returned loaded assemblies by a null-safe, ordinal assembly identity key. Prefer `Assembly.FullName`; use a stable fallback marker if unavailable and record the failure. If two assemblies have identical display identity, use a stable secondary key such as manifest module name and module version ID when safely available. If a deterministic distinction still cannot be made, preserve both records and mark ordering uncertainty/PARTIAL.
3. Apply the global 128-assembly inspection ceiling from the Resource Budget Addendum. If loaded assembly count exceeds the ceiling, emit TRUNCATED and PARTIAL. Do not imply that uninspected assemblies contain no target types.
4. Inspect each selected assembly independently. One assembly failure must not prevent inspection of later assemblies.
5. Emit one ASSEMBLY record per assembly considered, with identity, module identity where available, inspection outcome, and candidate/type counts where safely known.
6. Do not use `GetExportedTypes()` as the discovery source: non-public types may be required. Use one `GetTypes()` attempt per assembly; do not redundantly call both APIs.

### 3.1 `GetTypes()` and partial type-load failure

- On success, process the returned array with null checks.
- On `ReflectionTypeLoadException`, process every non-null entry in `Types`; null slots are skipped and counted.
- Record the exception category and a bounded summary of loader exception types. Do not serialize arbitrary exception messages or stack traces.
- A partial type array, null slots, or loader exceptions make the overall run PARTIAL even if all nine targets happen to appear in the surviving entries.
- If `Types` itself is unavailable or processing cannot safely continue, record an assembly-level ERROR and continue with other assemblies.
- Any other exception from `GetTypes()` is isolated to that assembly. Do not retry automatically (retry budget is zero).

## 4. Stable type identity and safe formatting

For every candidate, record:

- `Assembly.FullName` (or UNKNOWN);
- module name and, if safely available, module MVID;
- `Type.FullName` and `Type.Name`;
- declaring type for nested types;
- base type;
- visibility category (public, nested-public, nested-family, nested-assembly, nested-private, nested-family-or-assembly, nested-family-and-assembly, non-public/top-level, or UNKNOWN);
- interface/enum/class/value-type flags and abstract/sealed flags where safely available.

Treat `FullName`, `AssemblyQualifiedName`, module name, base type and declaring type as potentially unavailable or exception-producing. Formatting must be null-safe. Do not use `AssemblyQualifiedName` as the only identity field; preserve separate assembly and type fields.

Type-name formatting must be deterministic and unambiguous for arrays (rank included), pointers, by-reference types, generic definitions, constructed generic arguments, nested types and generic parameters. Apply recursion-depth 8 and generic-argument 16 ceilings per the resource budget. If a ceiling or formatting exception is reached, emit a stable fallback token plus ERROR/TRUNCATED context; never recurse indefinitely or silently emit a misleading simple name.

Sort type records ordinally by assembly identity, module identity, full type name, declaring type name, then a stable metadata token when available. If a stable tie-breaker is unavailable, preserve the records and flag ordering uncertainty rather than using object hash codes or runtime addresses.

## 5. Ambiguity and downstream member inspection

- Inventory and report all candidate identities before deciding whether a target can be resolved.
- Only a uniquely resolved target may receive the full target member inventory.
- For AMBIGUOUS targets, emit candidate TYPE records and an explicit ambiguity ERROR/status. Do not inspect one candidate as if it represented the target.
- For NOT_FOUND targets, emit an explicit target status. A missing required target makes the run PARTIAL.
- If an exact expected FullName is configured and multiple assemblies contain that exact FullName, the result remains AMBIGUOUS until an explicit assembly identity is also approved in the target specification.
- Do not infer ownership, registration role, lifecycle order, or runtime instance identity from type names or metadata alone.

## 6. Member inventory contract

For each uniquely resolved target type, inventory declared metadata only. Use declared-only binding flags and a consistent visibility policy that includes public and non-public instance/static members. Do not recursively duplicate inherited members in the target's declared-member list; record the base-type chain separately if safely available.

The shared ceiling is 64 members per resolved type across fields, properties, events, methods and constructors. The ceiling is not 64 per category. Sort each category deterministically before applying the shared budget. If the cap is reached, emit TRUNCATED and mark the run PARTIAL.

Record categories:

- **FIELD:** name, declaring type, field type, visibility, static/instance, readonly/literal flags.
- **PROPERTY:** name, declaring type, property type, index parameter signature if present, and metadata signatures/visibility/staticness for each available getter/setter. Never call either accessor.
- **EVENT:** name, declaring type, handler type, and metadata signatures/visibility/staticness for add/remove/raise methods when present. Never call accessors.
- **METHOD:** name, declaring type, return type, visibility, static/instance, abstract/virtual/final flags, generic arity, ordered parameter signatures and parameter attributes.
- **CTOR:** constructor signature, declaring type, visibility, static/instance and ordered parameter signatures. Never invoke it.
- **ENUM:** underlying integral type and named constants. Do not call `Enum.GetValues()` if it requires a full unbounded values array; enumerate names and retrieve literal constant metadata where supported, with per-enum cap 64. If a safe deterministic mapping cannot be established, record UNKNOWN/error rather than inventing values.

Per-method/accessor parameter ceiling is 16. If more parameters exist, emit a truncated signature marker and PARTIAL. Include parameter type, position, name if available, and relevant in/out/optional/params metadata. Do not serialize default objects or arbitrary values.

For member enumeration failures, isolate at the narrowest safe boundary. A failed category or member query must not abort unrelated categories/types. Do not invoke getters, setters, event add/remove methods, constructors, static constructors, methods, delegates or callbacks to obtain metadata.

## 7. Explicit side-effect prohibitions

The implementation must not:

- execute static constructors (including `RuntimeHelpers.RunClassConstructor`);
- instantiate target/game/Unity types or create Unity objects;
- invoke any constructor, method, property getter/setter, event accessor, delegate or callback;
- enumerate the Unity object graph, scenes, GameObjects or components;
- load/unload AssetBundles or scenes;
- call game APIs such as Landmark/ChunkPoint registration, spawn, removal or initialization methods;
- mutate world, save, inventory, player, network or multiplayer state;
- apply Harmony patches, reflection emit, dynamic code generation or assembly loading;
- inspect arbitrary runtime field values, heap contents, player data or world data.

Permitted operations are limited to loaded-assembly enumeration and reflection metadata queries needed for the allowlisted types and their declared signatures. Any proposed exception to this boundary requires a separate design and explicit user authorization.

## 8. Failure isolation and status model

### 8.1 Error records

Record operation, scope (run/assembly/type/member), stable identity context, exception type and a bounded sequence number. Avoid raw exception messages, stack traces and arbitrary object formatting. The global error-record ceiling is 32; after it is reached, set an internal error-overflow flag and ensure the terminal SUMMARY reports the overflow/truncation. Do not silently discard the fact that errors exceeded the cap.

### 8.2 Status semantics

- **COMPLETE:** all 9 required targets uniquely resolved; all required metadata categories attempted and completed; no ambiguity, missing targets, truncation, recoverable errors, skipped assemblies, ordering uncertainty or output/logger failures; terminal SUMMARY successfully emitted.
- **PARTIAL:** any required target is missing or ambiguous; assembly/type/member inspection is incomplete; any cap is reached; any recoverable exception occurs; ReflectionTypeLoadException or null type slots occur; any assembly is skipped; output truncates; or deterministic ordering cannot be guaranteed.
- **FAILED:** fatal inability to enumerate safely, maintain the output contract, or emit the terminal SUMMARY; unrecoverable logger/output failure; or internal invariant failure that prevents a truthful result.
- A legitimately empty category (for example, no declared events) is not an error and does not by itself make the run PARTIAL.
- NOT_FOUND and AMBIGUOUS are target outcomes, not terminal run statuses.
- The terminal status must be computed after all records and errors are accounted for. Reserve record/character capacity for SUMMARY. Never set a completion latch before scanning and summary emission have actually succeeded.

## 9. Output protocol

Use the versioned `UWE-META/1` UTF-8 line-oriented protocol and global limits in the Metadata Probe Implementation Plan:

- 128 assemblies inspected;
- 8 candidates per target name;
- 64 declared members per resolved type (shared category budget);
- 16 parameters per method/accessor;
- 64 enum constants per enum;
- recursion depth 8 and 16 generic arguments per node;
- 32 error records;
- 512 output records including SUMMARY;
- 48,000 UTF-16 code units globally and 2,048 UTF-16 code units per record, each enforced independently on both unescaped logical and final escaped serialized payloads (prefix and separators included; LF terminators excluded);
- zero automatic retries.

Required record families: RUN, ASSEMBLY, TYPE, FIELD, PROPERTY, EVENT, METHOD, CTOR, ENUM, ERROR, TRUNCATED, SUMMARY.

Escape backslash, pipe, tab, carriage return and line feed. Use invariant numeric formatting. Use `-` for missing and `UNKNOWN` for unavailable. Never emit arbitrary runtime values. Every serialized record kind consumes the 512-record global ceiling, including RUN, ERROR, TRUNCATED and SUMMARY; the 32-ERROR ceiling is additional. Reserve capacity for one final SUMMARY and any mandatory terminal diagnostic/truncation record. Global budgets are not reset per assembly or target. If a single record cannot fit safely, replace it with a bounded truncation/error record where possible and mark PARTIAL. If SUMMARY cannot be emitted, terminal status is FAILED.

The budgets bound probe-controlled work and output only. Reflection APIs may allocate complete arrays before caller-side limits apply, and synchronous calls cannot be reliably interrupted. Do not claim hard allocation or wall-clock guarantees.

## 11. Evidence boundary and unresolved questions

This metadata inventory can establish which matching types and declared members are visible in the loaded assemblies at scan time. It cannot establish:

- which manager owns or creates a type instance;
- call order, lifecycle sequencing, coroutine/async behavior or thread affinity;
- whether a method is a supported mod extension point;
- registration invariants, key normalization or bundle path conventions;
- uniqueIndex allocation/collision rules;
- save serialization or persistence behavior;
- host/client authority or multiplayer replication semantics.

Those require exact target-build assembly hashes and IL/call-site evidence. The existing Landmark API Evidence Matrix must be updated only from preserved metadata/IL artifacts with build provenance, not from names alone.

## 13. G0 design-review findings and clarifications — 2026-11-06

The cross-review against the Metadata Probe Implementation Plan, Resource Budget Addendum, Boundedness Audit and C# project constraints found three places where the original wording could produce inconsistent implementation. This addendum is normative and supersedes conflicting wording in earlier sections.

### 13.1 Candidate reporting versus the eight-candidate cap

The plan's requirement to discover/report every candidate does not mean emitting an unbounded number of TYPE records.

- Inspect each type returned by each successfully inspected assembly and increment an observed-candidate counter for every exact short-name match.
- Retain at most the globally best 8 candidate descriptors per target using a bounded ordered set keyed by the deterministic identity tuple in section 4. Do not retain an unbounded candidate list merely to sort it later.
- Emit the retained descriptors in deterministic order, and emit the total observed count when the complete inspected assembly set was successfully scanned.
- If the assembly inspection cap or an assembly/type enumeration failure prevents a complete candidate count, report the count as observed-so-far and total as UNKNOWN.
- If observed candidates exceed 8, emit TRUNCATED with the observed/total count, mark PARTIAL, and do not resolve the target—even if only one retained candidate would otherwise appear plausible.
- If stable identity formatting fails for a candidate, keep a bounded fallback descriptor and mark ordering uncertain/PARTIAL. Never use discovery order as a tie-breaker.

This preserves bounded memory while making duplicate detection truthful. It also reconciles the plan's “all candidates” discovery requirement with the output/candidate ceilings: every candidate is examined and counted when possible, while only a bounded deterministic sample of identities is emitted.

### 13.2 Property/event accessors and standalone methods

Reflection APIs that enumerate declared methods can also return property and event accessor methods. Avoid duplicate output and ambiguous budget accounting:

- Emit property getter/setter signatures only inside the PROPERTY record.
- Emit event add/remove/raise signatures only inside the EVENT record.
- Exclude those accessor MethodInfo objects from standalone METHOD records, identified through metadata association with the declared PropertyInfo/EventInfo.
- Count each property or event as one member against the shared 64-member budget; its embedded accessor signatures do not consume additional member slots. Their parameters still obey the per-signature 16-parameter limit.
- If accessor-to-property/event association cannot be established safely, do not guess: emit a bounded ERROR, preserve the method as standalone only if it can be proven not to be an accessor, and mark PARTIAL.

This rule prevents the same metadata method from being emitted twice and prevents the member budget from depending on whether a compiler generated accessors.

### 13.3 Enum constants versus literal fields

For enum target types:

- Emit named enum constants only through ENUM records, with the enum's underlying integral type and bounded constant list.
- Exclude the enum's compiler-generated literal constant fields from ordinary FIELD records; otherwise constants would be duplicated and consume both the field and enum budgets.
- Count each emitted named constant only against the per-enum 64-constant ceiling, not the 64-member shared budget.
- Preserve any non-constant declared fields, if present, as FIELD metadata.
- If names or raw constant values cannot be paired deterministically without executing code or materializing an unbounded values array, emit UNKNOWN/error and PARTIAL; do not infer numeric values from ordering.

### 13.4 Deterministic ordering and budget interaction

- For each assembly, sort its non-null Type descriptors by the stable identity tuple before candidate accounting/output. For global candidate retention, maintain a bounded top-8 ordered set across inspected assemblies.
- For each resolved target, enumerate category metadata once where feasible, sort each category by ordinal metadata identity, then apply the shared member budget in this fixed category order: FIELD, PROPERTY, EVENT, METHOD, CTOR. ENUM constants use their separate budget.
- Accessor association must be performed before METHOD sorting and budget application.
- If a reflection API materializes a full array before the caller can sort/cap it, retain the allocation caveat from section 9; do not claim the caller-side sort makes the underlying reflection call bounded.
- Stable identity tie-breakers must never use object hash codes, runtime addresses, or incidental discovery order.

## 13.7 Output-budget cross-review — 2026-11-09

Two output-contract edge cases are now explicit:

1. `SUMMARY.characters_emitted` counts the escaped serialized SUMMARY record itself. The writer must calculate it by bounded fixed-point iteration after all preceding records are fixed; the parser independently verifies it. Logical and escaped totals remain separate budgets.
2. The 32-error cap must not preserve the first 32 encountered descriptors. Retain the deterministic top-32 set by stable diagnostic identity and assign ERROR.sequence after sorting. If a stable key component is unavailable, mark ordering uncertain/PARTIAL rather than falling back to enumeration order.

TD26–TD27 are design acceptance requirements only. They have not been executed. G0 remains REVIEWED — APPROVAL PENDING; v0.1.3 remains NOT IMPLEMENTED.
