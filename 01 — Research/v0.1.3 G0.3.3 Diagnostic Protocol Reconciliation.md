# v0.1.3 G0.3.3 Diagnostic Protocol Reconciliation

## 1. Status and scope

This is a design-only reconciliation of the seven findings in [G0.3.2 Diagnostic Overflow and Determinism Audit](v0.1.3%20G0.3.2%20Diagnostic%20Overflow%20and%20Determinism%20Audit.md). It aligns the G0.3.1 budget proposal with the existing UWE-META/1 record grammar and reflection-safety rules.

This addendum is **PROPOSED — NOT NORMATIVE** until formal G0 approval. It does not authorize C# implementation, fixture execution, compilation, packaging, installation, game launch, or world mutation. No API compatibility claim is added.

## 2. Canonical ERROR descriptor and ordering key

The UWE-META/1 ERROR record contains these stable diagnostic fields:

- `scope`;
- stable parent metadata identity, represented in the output by the parent record reference assigned after ordering;
- `operation`;
- `exception_type`;
- `recoverable`.

The canonical pre-ID ordering key is exactly:

`(scope, stable_parent_metadata_identity, operation, exception_type, recoverable)`

All string components use ordinal, culture-independent comparison. The boolean uses a fixed FALSE-before-TRUE ordering. The run ID is common to one stream. The run-local `error_id`, `parent_id` reference and `sequence` are assigned only after the bounded inventory and diagnostic set have been ordered.

UWE-META/1 has no separate `error_code` field. Do not invent one, and do not treat `error_id` as an error code. The schema also does not require an occurrence-ordinal field.

If a key component is unavailable, use the schema's explicit `UNKNOWN` representation and set `ordering_uncertain=TRUE`; the run is at least PARTIAL. Never fall back to encounter order, thread order, hash codes, object addresses or current culture.

### Identical descriptors

Descriptors with equal canonical keys must have identical serialized diagnostic content before run-local IDs and sequence numbers are assigned. Treat them as a multiset and preserve multiplicity up to the 32-record cap. No occurrence ordinal is needed: equal descriptors are indistinguishable, and retaining up to 32 copies is independent of discovery order.

If two descriptors compare equal by the canonical key but differ in another serialized diagnostic field, treat that as an internal invariant violation and fail the run rather than choosing an arbitrary order.

## 3. Bounded deterministic top-32 retention

Maintain a sorted multiset containing at most 32 ERROR descriptors:

1. Construct the canonical descriptor without serializing or writing it.
2. Insert it using the canonical key.
3. If the set exceeds 32, discard the lexicographically greatest descriptor and set `error_cap_overflow=TRUE`.
4. Preserve duplicate multiplicity for equal descriptors up to the cap.
5. After discovery is complete, sort the retained descriptors and assign ERROR.sequence as 1..N in emitted order.

Track two independent bounded flags:

- `error_cap_overflow`: one or more observed descriptors were excluded by the 32-ERROR cap;
- `error_output_omission`: one or more retained descriptors could not be committed because ordinary record or character capacity was exhausted.

SUMMARY.`errors_overflow` is TRUE when either flag is TRUE. SUMMARY.`errors_emitted` counts only ERROR records actually committed. A saturating diagnostic-observation counter may be kept for TRUNCATED metadata; if it saturates or discovery is incomplete, any exact total that cannot be proven is UNKNOWN.

Both cap overflow and output omission force PARTIAL and require the aggregate terminal TRUNCATED record when that record can be committed.

## 4. Two-phase collection and serialization

The scan must not write ERROR or TRUNCATED records while reflection discovery is in progress.

**Phase A — bounded collection**

- Collect a bounded inventory plan and bounded diagnostic descriptors.
- Keep only the metadata required by the output schema.
- Record truncation causes and the two diagnostic-overflow flags.
- Do not retain arbitrary exception messages, stack traces or runtime object values.
- Stop collection when the relevant bounded inventory/output planning limits are reached; never continue by growing an unbounded buffer.

**Phase B — canonicalization and emission planning**

- Sort assemblies, types, members and other inventory records by the schema's stable ordering rules.
- Sort the retained ERROR multiset by the canonical key above.
- Sort scope-specific TRUNCATED descriptors by the existing deterministic scope/parent/budget/reason ordering.
- Assign run-local record IDs and ERROR.sequence only after the relevant bounded records have been ordered.
- Freeze one emission plan in the schema's required order: RUN, inventory, diagnostics, terminal records.

**Phase C — serialization**

- Serialize only the frozen plan.
- Inventory always precedes ERROR/TRUNCATED records.
- Do not insert a late diagnostic before already committed inventory.
- If inventory consumes all ordinary capacity, omit retained ERROR records deterministically, set `error_output_omission=TRUE`, set SUMMARY.`errors_overflow` TRUE and use the terminal reserve.
- Never serialize a partial record and then continue with later records.

The plan itself remains bounded by the existing 512-record, 48,000-code-unit global and 2,048-code-unit per-record ceilings. The design does not claim to bound allocations performed internally by Reflection APIs before they return.

## 5. Independent terminal-reserve accounting

Keep the G0.3.1 reserve unchanged:

- exactly two record slots;
- 4,096 UTF-16 code units reserved independently in the logical unescaped domain;
- 4,096 UTF-16 code units reserved independently in the escaped serialized domain.

The ordinary budget is therefore 510 records and 43,904 code units in each character domain. Charge every committed record's actual logical and escaped lengths independently. Do not use one shared 4,096 counter, and do not borrow unused capacity from one character domain to exceed the other domain's hard ceiling.

The two reserved slots are for at most one aggregate terminal TRUNCATED record and one final SUMMARY. Any earlier scope-specific TRUNCATED records consume ordinary capacity.

## 6. Terminal truncation reason and SUMMARY semantics

The TRUNCATED schema has one bounded `reason` token. Use only existing reason tokens; this proposal does not add a new `ERROR_OVERFLOW` reason or any new field.

When several causes must be coalesced into the one aggregate terminal TRUNCATED record, select exactly one primary reason using this fixed precedence:

1. `OUTPUT_BUDGET` — ordinary record or character capacity prevented serialization;
2. `ENUMERATION_INCOMPLETE` — required enumeration did not complete;
3. `IDENTITY_UNAVAILABLE` — a required stable identity was unavailable;
4. `LIMIT_REACHED` — a local/global processing limit was reached, including the 32-ERROR cap.

For an ERROR-cap-only condition, use `reason=LIMIT_REACHED`, `budget_name=ERROR_RECORDS` and `limit=32`. For ordinary output-cap omission, use `reason=OUTPUT_BUDGET` and the applicable output budget name. Do not concatenate reason strings or invent exact omitted counts. Use UNKNOWN for `observed` or `total` when an exact value is not safely known. Secondary causes are coalesced and are not implied to be individually listed in the single reason field.

Emit exactly one aggregate terminal TRUNCATED record whenever any output omission, ERROR overflow or budget-triggered truncation makes the run PARTIAL, provided the reserved writer path remains available. Earlier scope-specific TRUNCATED records may also be emitted from ordinary capacity. SUMMARY.`truncations` counts every TRUNCATED record actually committed, not the number of underlying causes.

All SUMMARY counters describe the committed stream:

- `errors_emitted`: committed ERROR records only;
- `errors_overflow`: TRUE if either ERROR-cap exclusion or output-cap omission occurred;
- `truncations`: committed TRUNCATED records only;
- `records_emitted`: every committed record, including RUN and SUMMARY exactly once;
- `characters_emitted`: final escaped serialized payload length, including SUMMARY itself and excluding LF terminators, calculated by the bounded fixed-point rule and independently recomputed by the parser.

Buffered, attempted or dropped records must never be counted as emitted.

## 7. Writer commit and failure semantics

A record is committed only after the writer abstraction confirms acceptance of the complete serialized payload and its required line terminator. A partial byte/character write is not a committed record.

On any writer/logger failure:

- stop ordinary serialization immediately;
- do not continue on the failed sink;
- do not claim that reserved capacity guarantees recovery;
- mark the run FAILED if truthful completion cannot be established;
- do not emit a SUMMARY that claims a valid committed stream when the writer has failed.

A terminal write may be attempted only if a separately specified and independently verified recovery sink exists. No such recovery sink is currently designed. Otherwise the stream has no valid final SUMMARY and the parser's missing/non-final SUMMARY rule yields FAILED.

## 8. Required regression tests

These are design acceptance requirements only; none has been executed.

| ID | Scenario | Expected result |
|---|---|---|
| G033-T01 | The same 40 distinct ERROR descriptors are discovered in multiple shuffled orders | Identical retained top-32 set and serialized order |
| G033-T02 | More than 32 byte-identical ERROR descriptors are discovered | Retain 32 identical copies; overflow TRUE; no occurrence ordinal or arrival-order tie-break |
| G033-T03 | A required stable parent identity is unavailable | Explicit UNKNOWN key component; ordering_uncertain TRUE; PARTIAL; deterministic output |
| G033-T04 | Two diagnostics differ only by exception type or recoverable flag | Canonical key distinguishes them and sorting is stable |
| G033-T05 | ERROR cap overflow and ordinary output-cap omission occur separately and together | errors_overflow TRUE for either condition; counters reflect only committed ERROR records |
| G033-T06 | Inventory consumes all ordinary capacity before diagnostics | Inventory order preserved; omitted ERRORs are not counted; terminal TRUNCATED uses reserve |
| G033-T07 | Logical and escaped output budgets reach their reserve boundaries at different points | Each domain is enforced independently; neither borrows from the other |
| G033-T08 | Multiple truncation causes occur in different discovery orders | Same primary reason by fixed precedence; truncations counts committed TRUNCATED records |
| G033-T09 | Writer fails midway through a record | Partial record not counted; run FAILED; no false SUMMARY |
| G033-T10 | Parser recounts a complete fixture with SUMMARY and terminal TRUNCATED | Record/error/truncation counters and escaped character fixed point match exactly |

## 9. Disposition

G0.3.3 resolves the design inconsistencies identified by G0.3.2 at proposal level. It does not establish that the proposed writer/parser is implemented or correct in execution.
