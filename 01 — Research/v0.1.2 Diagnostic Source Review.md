# v0.1.2 Diagnostic Source Review and v0.1.3 Research Requirements

## Scope

This review is based only on the two repository copies of `RaftUltimateWorldExpansion.cs` and `modinfo.json`. The Core and RML source files were byte-for-byte represented by the same Git blob in the repository at review time (SHA recorded in GitHub fetch metadata). No compilation, game launch, local file access, or runtime test was performed.

The review describes what the source attempts to inspect. It does not claim that v0.1.2 has run in-game.

## 1. What the current probe does

- Waits for `WorldEvent_WorldLoaded()` and runs once per mod instance.
- Locates loaded types by short type name across loaded assemblies.
- For UnityEngine.Object-derived manager types, enumerates loaded objects and chooses the first component attached to a valid scene.
- Reads a bounded set of named manager fields.
- Enumerates up to 8 ChunkPoint dictionary keys, 12 points per key and 20 spawner entries.
- Reads up to 18 declared instance fields from each enumerated object.
- Enumerates up to 24 declared fields and 32 declared methods for selected types.
- Logs enum values for ChunkPointType.
- Does not call game spawn, bundle-load, save-write, or network methods.

## 2. Source-level limitations

| Area | Current behavior | Consequence |
|---|---|---|
| Type discovery | Searches all loaded assemblies by short type name | Ambiguous duplicate type names are not reported; assembly identity is missing |
| Manager ownership | Selects first Unity component in a valid scene; non-Unity types have no instance | Does not establish singleton/service ownership, inactive object ownership, or creation call sites |
| Field coverage | Declared fields only; capped at 24 for type surface and 18 for runtime objects | Inherited fields and fields beyond caps may be missed |
| Method coverage | Declared methods only; capped at 32 | Constructors, properties/accessors as a grouped contract, inherited methods and excess overloads may be missed |
| Signatures | Parameter and return types are logged using Type.Name | Namespace and assembly identity are lost; generic and nested type signatures may be ambiguous |
| Method semantics | No IL or caller/callee inspection | Cannot establish registration behavior, call order, side effects or authority |
| Landmark types | Selected type list omits Landmark, LandmarkData and AsyncedLandmark | The key data contracts in the proposed content pipeline are not fully described |
| Bundle pipeline | No bundle bytes are loaded or inspected | Does not validate embedded-file path, bundle key, scene path or Unity compatibility |
| Retry behavior | `worldProbeCompleted` is set before inspection begins | A partial failure will not automatically retry on a later WorldLoaded callback in the same mod instance |
| Output completeness | Per-object and per-type caps are fixed | Truncated output must be treated as partial, not as proof that no member exists |

These are source-level observations, not runtime failures. The probe was deliberately read-only and bounded; the omissions are expected limitations of its current scope.

## 3. Recommended v0.1.3 research-only scope

The next diagnostic revision, if/when a user-authorized local build becomes possible, should remain read-only and add only metadata coverage:

1. Report assembly-qualified identity for each discovered target type and detect duplicate short names.
2. Inspect these types: `Landmark`, `LandmarkData`, `AsyncedLandmark`, `SceneLoader`, `AssetBundleManager`, `AssetBundleHooker`, `ChunkManager`, `ChunkPoint`, and `ChunkPointType`.
3. Include constructors, declared fields, properties/accessors, events, and method overloads with full parameter and return type names, visibility and static/instance flags.
4. Record base types and declaring assemblies.
5. Keep output limits configurable and log explicit truncation counts.
6. Avoid invoking constructors, property getters, game methods, Unity object creation, bundle APIs, or reflection emit.
7. Do not infer manager ownership or call order from field presence; that still requires offline IL/call-site analysis.
8. Preserve exception isolation per type/member so one inaccessible member does not abort the remaining metadata scan.

A runtime metadata dump can improve the evidence inventory, but it cannot replace offline IL analysis of manager creation, registration, uniqueIndex allocation, serialization, and network authority.

## 4. Do not add these behaviors to v0.1.3

- No `AssetBundle.LoadFromMemory` call.
- No calls to `LoadAssetBundle`, `AddLandmarksToHooker`, `LoadScenes`, `AddLoadedLandmark`, `TrackAddressableLandmark`, or `InitializeLoadedLandmark`.
- No `ChunkPoint` insertion, spawn, or removal.
- No new `ChunkPointType`.
- No save-data writes, network messages, patches, Harmony hooks, or scene instantiation.

## 5. Version and status policy

The repository's current RML source and modinfo report version 0.1.2. This source review does not change that version and does not authorize a v0.1.3 package.

A future v0.1.3 should be called a metadata-coverage diagnostic only. It must not be described as a custom Landmark prototype.

## Decision

The next safe implementation unit is a bounded metadata-only diagnostic improvement, but it is deferred while the project remains repository-only. Before a v0.1.3 code change, obtain the actual target-build metadata/IL or explicitly authorize the local workflow needed to generate it. Custom Landmark registration remains blocked.
